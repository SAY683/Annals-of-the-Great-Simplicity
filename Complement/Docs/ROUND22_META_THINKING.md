## 1. 核心发现: "声明-实现鸿沟" (Statement-Implementation Gap)

### 1.1 缺陷定义

**现象**: 上一轮会话总结明确描述了修复的代码片段和文件路径，但本轮 Read/Grep
复检时发现目标文件中 **不存在** 这些修改。

**影响范围** (本轮复检发现的 7 处"声称已修复但实际未写入"):

| # | 文件 | 声称的修复 | 实际状态 |
|---|------|-----------|---------|
| 1 | `edm-takens-web/start_mvp.py` | 添加 dist 目录检测，条件启动 Vite | 未写入，仍无条件启动 Vite |
| 2 | `trace-engine-web/llama_worker.py` | TRACE 内部进度映射到 [0.2, 0.5] | 未写入，仍发送 [0,1] 范围 |
| 3 | `trace-to-edm/public/css/main.css` | work-scan-wrap 提升到 56vh | 未写入，仍为 32vh |
| 4 | `trace-to-edm/public/css/main.css` | terminal max-height 限制为 42vh | 未写入，仍为 none |

| 6 | `trace-engine-web/py_bridge.py` | max_delta_nll 保存归一化前原始值 | 未写入，仍读取归一化后值 |
| 7 | `edm-takens-web/frontend/src/main.js` | 添加进度条和结果面板导出按钮 | 未写入，无进度条无导出按钮 |

也未写入（隧道模式分支有，本地模式分支缺失）。

### 1.2 根因分析

**根因 1: 上下文压缩导致修复丢失**
- 长会话接近上下文限制时，系统自动压缩历史消息
- 压缩可能丢弃了 Edit/Write 工具调用的执行细节
- 总结基于"意图"而非"实际执行结果"生成

**根因 2: 子代理返回值被无条件信任**
- 上一轮可能使用了 Task 子代理执行修复
- 子代理返回"已修复"声明，主代理未 Read 验证
- 子代理的"成功"声明可能是幻觉或部分执行

**根因 3: 缺少"修改后验证"强制步骤**
- 修复流程缺少闭环: Edit → Read 验证 → 标记完成
- 直接从 Edit 跳到"标记完成"，跳过了验证

### 1.3 方法学缺陷的投影

用户原话: *"我们（五大项目的'统一方法论'）作为循环排查的遗漏，
它不仅是显著的问题，更是我们'整体方法的缺陷和错误（这是我们整体的投影而已）'"*

**投影解读**:
- "统一方法论"假设修复声明 = 代码实际变更 → **错误假设**
- "循环排查"假设上一轮已修复的问题不需要复检 → **错误假设**
- 这两个错误假设导致问题在多轮中反复出现而不被发现

## 3. 4 角色互审

### PM 视角

**最大风险**: "声明-实现鸿沟"意味着之前所有轮次的"已完成"清单都不可信。
必须对 Round 18-21 的关键修复做抽样复检。

**用户信任损失**: 用户反复报告"已修复"的问题，说明我们的修复流程存在系统性缺陷。
这不是个别疏漏，而是方法论的投影。

### 算法工程师视角

**max_delta_nll 恒为 8.0 是严重算法 bug**: 这个值是轨迹 CSV 的核心区分指标，
所有行相同意味着下游 EDM 分析无法区分不同时间点的因果信号强度。
此 bug 可能从项目初期就存在，影响了所有历史分析结论。

**SUPER 模式进度回跳**: 进度条回跳会让用户误以为任务失败或卡住，
可能导致用户主动取消正在正常运行的任务。

### 测试工程师视角

**缺失的测试环节**: 修复后没有"端到端验证"步骤。应在每个修复后:
1. Read 验证代码已写入
2. 启动服务验证功能生效
3. 截图/日志确认用户体验改善

**建议**: 建立"修复-验证-归档"三阶段强制闭环。

### 方法论审计视角

**"循环排查"的致命假设错误**:
- 假设: 上一轮修复的问题不需要本轮复检
- 现实: 上一轮声称的修复有 7/8 没有实际写入
- 后果: 问题在多轮中反复出现，用户反复报告同一问题

**改进**: 每轮必须包含"上轮修复复检"步骤，即使总结声称已完成。

## 4. 改进措施 (强制流程)

### 4.1 修复-验证闭环 (MUST)

```
Edit/Write → Read 验证 → (如需) Grep 确认 → 标记完成
```

- **禁止**: Edit 后直接标记完成
- **禁止**: 信任子代理返回的"已修复"声明而不验证
- **必须**: Read 修改后的文件，确认修改已写入

### 4.2 跨轮复检协议 (MUST)

每轮开始时，必须对上一轮声称的修复做抽样复检:
- 抽样率: ≥30% 的"已完成"项
- 复检方式: Read/Grep 目标文件，确认修改存在
- 若发现"声明-实现鸿沟"，全量复检上一轮所有修复

### 4.3 总结生成规则 (MUST)

总结必须基于"实际执行结果"而非"意图":
- 引用实际写入的代码行（含行号）
- 标注"已 Read 验证"或"未验证"
- 禁止使用"应该已修复"等不确定措辞
