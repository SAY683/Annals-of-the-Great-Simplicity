## 1. "不盲信文档"原则的实证

### 1.1 项目记忆 vs 真实代码

**事件**: 项目记忆中长期记录 "trace-to-edm/server.js header comments must accurately reflect the current number of endpoints (29)", 但 Round 19 代码审视发现:

- `trace-to-edm/server.js:9` header comment 明确写 "共 31 个 API 端点"
- 用 `grep app\.(get|post|put|delete|patch)\s*\(` 统计, 实际 31 个端点
- 项目记忆中的 "29" 是过时/错误值

**校正**: 在 MICROSERVICE_API_DESIGN.md §6.1 表格中把 29→31, 合计 77→84。

**元教训**:
1. **文档措辞会干扰判断**: "PCA 中心化修复"听起来像已实现 Procrustes, 实际只是 mean centering 占位
2. **项目记忆也会过时**: 长期记忆中的数值需要定期用代码审视复核
3. **复核方法**: `grep app\.(get|post|put|delete|patch)\s*\(` 是验证端点数的可靠方法

### 1.2 Round 17 设计 vs Round 19 真实状态

Round 17 设计了 R-algo_4 (PCA Procrustes) 并标注 "待 Phase 2 实施", 但 Round 19 审视发现:
- `layer2_semantic.py:230-235` 只做了 `embedding - mean` (mean centering)
- 真正的 Procrustes (旋转/缩放/平移使两组 PCA 主轴对齐) 完全未实现
- 文档措辞 "PCA 中心化修复" 容易误导为已实现 Procrustes

**元教训**: 设计文档中的 "待实施" 与 "已实施" 边界模糊, 后续 Round 容易把 "已设计" 误传为 "已落地"。校正方法: 用 `Read` 工具直接看代码, 而非依赖文档措辞。

## 2. 算法审视的 4 项隐藏债务

通过"不盲信"审视, 发现 Round 17 设计中 4 项被掩盖的债务:

| 编号 | 隐藏原因 | 真实状态 |
|------|---------|---------|
| D1 (Procrustes) | 文档措辞 "PCA 中心化修复" 误导 | 仅 mean centering, 非 Procrustes |
| D3 (VERIFIABLE) | 三级语义框架已落地, 看似完整 | `_deploy_ccm` 未实际调用, VERIFIABLE 永不触发 |
| D4 (CCM 反向冲突) | `pass` 语句在 5 行代码中, 不显眼 | 真实方向冲突被漏报 |
| D5 (收敛检测) | 5 次迭代看似合理 | 无收敛检测, 极端环下不收敛 |

**元教训**: 算法审视不能只看 "框架是否落地", 必须看 "关键路径是否真实执行"。D3 的三级判定框架本身没问题, 但 `_deploy_ccm` 的内部调用缺失让 VERIFIABLE 沦为死代码。这类 "形似神不似" 的债务最隐蔽。

## 3. 手动/自动测试边界的设计理念

### 3.1 用户核心理念

用户提出: "作为测试，不应该完全依靠脚本{应该分层次和功能，什么是我们手动的，什么是我们自动的，应该有边界}"。这是一个测试设计理念, 而非具体技术要求。

### 3.2 边界划分原则

经 Round 19 实践, 总结边界划分原则:

**自动 (脚本/CI) 适合**:
- 数值正确性: `||V_proj R - V_bg||_F ≤ ε` 这类数学断言
- 管线跑通: 无崩溃 + 返回预期 schema
- 数值不退化: 固定 seed 下 ρ/consensus/SHD 与基线对比

**手动 (人工/E2E) 适合**:
- 用户认知正确性: 用户能否从 VERIFIABLE 标签理解 "这个因果方向被真算法验证过"
- 美学一致性: 红色 ERROR 与青色 VERIFIABLE 的色彩冲突是否破坏特摄终端氛围
- 显示比例: 75%/100%/150% 缩放下是否出现挤压/重叠 (脚本难以判断 "美不美")

**边界原则**: 脚本只验证 "数值正确性", 人工验证 "用户认知正确性与美学一致性"。

### 3.3 实践验证

Round 19 浏览器 E2E 测试中:
- 自动化能验证: 首页布局加载、跨项目导航链接、下拉框 disabled 状态 ✓
- 自动化难以验证: 缩放下的美学一致性 (截图工具不可用导致 BLOCKED) ✗
- 自动化限制: 按钮坐标超出视口 (Round 18 P3-18b 已知问题, 非真实 UI bug)

**元教训**: 浏览器自动化在 "判断按钮是否可点击" 上有视口限制, 但在 "判断元素是否存在/状态是否正确" 上可靠。设计 E2E 时应扬长避短。

## 4. z-index 层级体系的建立

### 4.1 问题背景

Round 18 发现 Toast 提示不可见 (z-index 冲突), Round 19 系统性建立层级:

| 层级 | z-index | 用途 |
|------|---------|------|
| CRT overlay | 999 | 扫描线特效 |
| SUPER 模式脉冲边框 | 9998 | 全屏边框动画 |
| modal-overlay | 10000 | 模态框遮罩 |
| toast | 10001 | 顶部提示 (最高, 始终可见) |

### 4.2 元教训

z-index 不是 "设个高数字就行", 而是需要建立明确的语义层级。后续新增浮层时, 必须先查现有层级表, 避免数字跳跃式增长 (如 9999 → 10001 → 9998 → 10000 这种混乱)。

## 6. 端点数对账的方法论

### 6.1 三处不一致

MICROSERVICE_API_DESIGN.md 中端点数曾有 77 / 84 / 29+24+31 三处描述:
- 文档头部: "29 + 24 + 31 端点" = 84 ✓
- §1.1 表格: 29 / 24 / 31 ✓
- §6.1 表格: 25 / 23 / 29 / 合计 77 ✗ (过时)

### 6.2 元教训

文档中同一数据多处出现时, 容易出现部分更新部分滞后的情况。解决方法:
- 单一真相源: 端点数应从 `server.js` header comment 动态读取, 而非多处硬编码
- 或用 Markdown 引用语法: "见 §1.1 表格", 避免重复
- 定期用 `grep app\.(get|post|put|delete|patch)\s*\(` 对账

## 7. Phase 1/2/3 落地优先级的方法论

### 7.1 排序依据

按 "辨别性收益 × 实现成本 × 风险" 三维排序, 而非单一维度:

| 维度 | 高优先级特征 | 低优先级特征 |
|------|------------|------------|
| 辨别性收益 | 15-25% (Procrustes) | <2% (Wolf 算法) |
| 实现成本 | 低 (D4-fix 改 pass 为判断) | 高 (TRACE daemon IPC 重设计) |
| 风险 | 低 (回退到 mean centering) | 高 (OPT-6 破坏向后兼容) |

### 7.2 元教训

- **辨别性收益是首要维度**: 算法的核心价值是 "压榨辨别性", 收益低的优化再便宜也不急
- **成本与风险并重**: 低成本但高风险 (OPT-6 Attention) 也不应列为 P1
- **依赖关系决定顺序**: D3-fix 依赖 ccm_with_convergence, 必须先确认依赖可用

## 8. 总结: Round 19 的元思考贡献

1. **"不盲信" 不是口号, 是可操作的方法**: 用 `Read`/`Grep` 直接看代码, 用 `grep app\.(get|post)` 验证端点数, 用具体行号反驳文档措辞
2. **"形似神不似" 债务最隐蔽**: D3 三级语义框架完整但 VERIFIABLE 永不触发, 这类债务需要看 "关键路径是否真实执行" 而非 "框架是否落地"
3. **手动/自动边界是设计理念**: 脚本验证数值, 人工验证认知与美学, 边界清晰才能各司其职
4. **文档单一真相源**: 同一数据多处硬编码必然漂移, 应动态读取或用引用语法

**下一步应用**: Phase 1 落地时, 每项 P1 任务完成后需用 "不盲信" 方法复核: 实际看代码是否真落地, 而非依赖 PR 描述或 commit message。
