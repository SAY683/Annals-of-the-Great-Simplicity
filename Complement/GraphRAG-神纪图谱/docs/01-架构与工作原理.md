# 01 · 架构与工作原理

## 1. 整体链路

```
神纪_合并版.md (470KB, 24万字符)
        │  分块 (1200 token, overlap 100) → 119 块
        ▼
  实体/关系抽取 (deepseek-v4-flash, reasoning_effort=none)
        │  每块抽取实体+关系，带 10 类 entity_types
        ▼
  描述总结 (summarize_descriptions)
        │  对每个实体/关系的描述去重、合并、压缩
        ▼
  图谱构建与社区发现 (Leiden 分层聚类)
        │  500 个社区（level 0~4）
        ▼
  社区报告生成 (community_reports)
        │  每社区一份 JSON 报告（标题/摘要/结论/发现）
        ▼
  向量化 (本地 bge-m3, 1024 维)
        │  entity_description / community_full_content / text_unit_text
        ▼
  LanceDB 向量库 + parquet 成品
```

## 2. 四大检索方法

| 方法 | 原理 | 适用 |
|---|---|---|
| Local | 以实体为中心，取邻居/关系/相关文本 + 向量召回 | 问具体实体、概念 |
| Global | 分层社区报告做 map→reduce 全库综合 | 问整体主题、跨文本思想 |
| Drift | 多跳扩展搜索（local + 迭代外扩） | 复杂、开放性问题 |
| Basic | 纯向量检索文本块 | 原文片段定位 |

## 3. 关键设计决策（为什么这样配）

1. **LLM 实际走 DeepSeek 官方 API**（deepseek-v4-flash）。配置里的 `127.0.0.1:15721`
   是 CC Switch 本地代理，实测按 Codex 类型路由到官方 DeepSeek（`api.deepseek.com`）；
   opencode Go 只出现过 1 个请求，并未承担全量构建。原"0 元 opencode 订阅"结论有误。
2. **`reasoning_effort: none` 是命门**：deepseek-v4-flash 默认思考全开，
   会把全部 max_tokens 烧在 thinking 上、输出为空。关闭后单块 ~40s。
   （详见 `04-维护与故障排查.md` 的"为什么快"一节）
3. **本地 bge-m3 做向量**：1024 维，FP16 GGUF，llama-server 托管（端口 8081）。
   向量不上云，隐私与成本可控。
4. **10 类自定义实体**而非默认 4 类：神学文本的"概念/神祇/象征"远多于"组织/人物/地点/事件"，
   默认 4 类会造成严重错位（如"爱"被标成 organization）。

## 4. 组件依赖图

```
AI 宿主 (Codex/Claude/Cursor)
   │  MCP (stdio)
   ▼
graphrag_mcp.py
   │  调用 graphrag query CLI
   ▼
graphrag (Python 包)
   ├── LLM 通道 → DeepSeek 官方 API (api.deepseek.com，deepseek-v4-flash；可经 CC Switch 代理 15721)
   └── 向量通道 → llama-server (127.0.0.1:8081) → bge-m3 FP16
```

## 5. 本归档如何保持便携

- `mcp\graphrag_mcp.py` 用 `Path(__file__).parent.parent / "project"` 定位项目 → 整个文件夹可随意移动。
- `scripts\*.ps1` 同理用 `$PSScriptRoot` 定位，并用环境变量提供路径覆盖点。
- 唯一外部依赖（llama-server、DeepSeek API、Python）均有默认路径 + 环境变量可改；CC Switch 代理可选。
