# 04 · 维护与故障排查

> 维护原则：**任何修改前先备份**（Move-Item 旧目录，勿删）；改配置后按需重建索引。

## 1. 症状速查表

| 症状 | 原因 | 处理 |
|---|---|---|
| 查询报"Project ... has no output/ directory" | GRAPHRAG_PROJECT 被设为错误路径 / 默认路径未命中 | 显式传 `project=` 参数；或检查环境变量 |

| 查询超时/无响应 | LLM 通道不可用 / embedding 服务未启动 | 启动 `00-start-embedding.bat`；确认官方 DeepSeek key 有效，或代理 15721 在线 |
| 输出为空但 usage 全是 reasoning_tokens | 丢了 `reasoning_effort: none` | 检查 settings.yaml `call_args.extra_body.reasoning_effort: none` |
| 重建时大量"Community Report Extraction Error" | 模型输出 JSON 带围栏/尾逗号/未转义引号 | 确认 `community_reports_extractor.py` 三层容错补丁在位（见下） |
| DeepSeek / CC Switch 限流 | 官方 API 429 或代理配额 | 降 `concurrent_requests` 到 12；或换时段 |

## 6. 顽固社区报告的处理方法

个别社区（如 379）可能因上下文特殊而持续失败。处理：
1. 用 GraphRAG 自己的上下文构建器复现生成（`build_local_context` + `build_level_context`）。
2. 将结果补插 `community_reports.parquet`（需按 schema 生成 `id`=sha512(full_content)、
   `human_readable_id`=community、parent/children/size/period 取自 communities 表）。
3. 同步向 `lancedb/community_full_content.lance` 补一条 1024 维向量（用本地 bge-m3 生成）。
完整代码模式见 `图谱项目训练经验归档.md`。

## 7. 常见配置陷阱

- 改了 embedding 模型忘了改 `vector_size` → LanceDB 维度不一致报错。
- `api_key` 对 CC Switch 代理无所谓（填 `dummy`）；直连 DeepSeek 时必须用 `GRAPHRAG_API_KEY`。
- 中文路径在部分工具链（PowerShell→python 管道）会乱码 → 用环境变量传路径，或保持归档路径全 ASCII。

## 8. Windows 中文编码大坑（本归档曾踩过）

**现象**：部分文档出现大段 `?`（中文全部丢失）。审计脚本见下方。

**根因**：`PowerShell 管道 -> python stdin`（如 `@'...'@ | python -`）时，PowerShell 用控制台代码页（GBK）把中文写入管道，python 读到的中文变成 `?`。凡是用这种管道写的文件都会损坏。

**安全写法**（本归档已全部按此修正）：
- 写文件用 **PowerShell `Set-Content -Encoding UTF8`**（here-string 内存中是 Unicode，可靠）
- 给 python 传中文参数/路径用**环境变量**（`$env:XXX = '中文'`，python 读 `os.environ`）
- 不在 `@'...'@ | python -` 的 heredoc 里放中文

**快速审计**（检测整目录是否有中文损坏）：
```python
import os, re
for root, _, files in os.walk(r"."):
    for fn in files:
        if fn.endswith((".md", ".ps1", ".py", ".txt")):
            t = open(os.path.join(root, fn), encoding="utf-8", errors="replace").read()
            if t.count("\ufffd") or re.search(r"\?\?{2,}", t) and not re.search(r"[\u4e00-\u9fff]", t):
                print("CHECK:", os.path.join(root, fn))
```
（2026-08-05 实测：修复 3 个文件后全目录 0 损坏。）

## 9. 分块器边界 U+FFFD（tiktoken 解码伪影）

**现象**：`text_units.parquet` 中约 0.013% 字符（14 个）被替换为 U+FFFD，多出现在**块首**。

**根因**：`split_single_text_on_tokens`（graphrag\index\text_splitting\text_splitting.py）用 tiktoken 按 token 切块后 `decode()` 还原文本——当 overlap 切点落在多字节 UTF-8 序列中间时，tiktoken 解码产生 U+FFFD。源文本（documents.parquet）始终干净，这是**分块器解码伪影**，不是数据损坏。

**影响**：basic / drift 搜索的文本块轻微失真；向量库中对应块的向量略有偏差。

**修复（2026-08-05 已执行，源 + 归档同步）**：
1. 用 `documents.parquet`（干净全文）按上下文还原每个 U+FFFD 为正确字符；
2. 校验修复后的块是文档的干净子串（全部通过）；
3. 对受影响的 13 个块重新生成 bge-m3 向量，更新 `text_unit_text.lance`（delete+add，行数保持 119）。

**预防**：若重建索引后再次出现，可对 `split_single_text_on_tokens` 的 `decode` 结果做后处理（对块首/块尾的 U+FFFD 用相邻块上下文修正）；或用非 token 型 chunker（如按分隔符）。

## 10. 检索侧 response_format 兼容（DeepSeek 官方/代理）

**现象**：`--method drift` 曾报 `HTTP 400: This response_format type is unavailable now`
（CC Switch/DeepSeek 不支持部分 response_format 类型）。

**根因**：部分 GraphRAG 检索路径硬编码 `response_format` 或
`response_format_json_object`，而 provider 并不保证支持这些参数。

**当前方案（推荐，正常流程）**：不修改 `site-packages`。查询、索引与 MCP 统一通过
`scripts/graphrag_compat_cli.py` 进入，在 GraphRAG 导入前安装运行时能力兼容层：

1. 按 provider/model/API base 探测 JSON response mode 能力；
2. provider 拒绝 `response_format` 时自动去掉该参数并重试一次；
3. 统一容错解析 Markdown 围栏、说明文字和尾逗号；
4. 覆盖 sync/async/batch/thread-pool 四条 completion 路径。

**效果**：global / local / basic / drift 四种检索均通过兼容入口验证。详细设计和覆盖范围见
[07-provider-compatibility.md](07-provider-compatibility.md)。

**原则**：正常安装、升级和排障都先使用兼容入口，不再要求修改第三方包。只有诊断旧版
GraphRAG 环境时，才可临时使用下述 legacy 脚本。

## 11. 旧版 site-packages 补丁（仅排障兜底）

`scripts/reapply-graphrag-patches.py` 保留用于无法使用兼容入口的旧环境诊断。它不是正常

## 12. 本地 15721 代理要求 `x-opencode-session`

若查询报：

```text
Request is missing x-opencode-session and cannot be routed efficiently
```

说明当前本地代理路由到了需要该头的上游。`project/settings.yaml` 已在两个 completion model 的 `call_args.extra_headers` 中加入：

```yaml
extra_headers:
  x-opencode-session: complement-graphrag
```

若代理仍不可用，改用官方 DeepSeek：把 `api_base` 改为 `https://api.deepseek.com`，并通过本地 `.env` 或环境变量提供 key。不要把 key 写入仓库。

## 13. U+FFFD 修复与数据版本

- `scripts/repair-text-units.py` 会从 `documents.parquet` 的干净全文定位并修复 `text_units.parquet` 中的 U+FFFD。
- 修复后 `text_unit` 的 sha512 id 会变化，脚本会同步重映射 `entities/relationships/documents/communities` 的 `text_unit_ids`。
- `--rebuild-vectors` 会重新生成 `text_unit_text.lance` 的全部向量；需要先启动 8081 bge-m3 服务。
- `project/output/data_version.json` 记录 `generated_at`、计数、`repaired_chars`、`remapped_ids` 和 `text_unit_hash`。
- MCP 的 `graphrag_get_data_quality` 可直接读取这些信息。
