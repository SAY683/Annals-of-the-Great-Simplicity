## 三、核心经验与踩坑记录（按重要性排序）

### 1. 【关键】实体类型（entity_types）必须贴合语料领域
- **现象**：默认 `[organization, person, geo, event]` 用于神学文本严重错位——"爱"被标 ORGANIZATION、"雨"被标 EVENT、"吠陀"被标 EVENT。
- **根因**：GraphRAG 将 entity_types 直接拼接进抽取 prompt，不做映射；英文通用预设不适用中文神学/象征文本。
- **解决**：自定义为 `[concept, deity, person, place, symbol, event, scripture, organization, object, natural_element]`。
- **效果**：实体从 358 → 1623（4.5 倍），关系 453 → 4361（9.6 倍），问答深度显著提升。
- **经验**：5–15 个类型是甜区；类型越少漏抽、越多则模型分类混乱。**领域语料必须先做 prompt-tune / 自定义类型**。

### 2. 【关键】DeepSeek 不兼容 json_schema（社区报告生成失败）
- **现象**：`create_community_reports` 报 `BadRequestError: This response_format type is unavailable now`，随后 `KeyError: 'community'`。
- **根因**：GraphRAG 社区报告默认传 `response_format=CommunityReportResponse`（Pydantic → json_schema），DeepSeek 只支持 `json_object`，不支持 `json_schema`。
- **解决**：打补丁 `community_reports_extractor.py`：改用 `response_format_json_object=True` + 手动 `model_validate_json`。
  ```python
  response = await self._model.completion_async(messages=prompt, response_format_json_object=True)
  output = (CommunityReportResponse.model_validate_json(response.content) if response.content else None)
  ```
- **注意**：补丁文件在 `G:\Python\Lib\site-packages\graphrag\index\operations\summarize_communities\community_reports_extractor.py`，**升级 GraphRAG 会被覆盖，需重新打补丁**（备份 `.bak`）。
- **经验**：国内模型（DeepSeek/Kimi）对 OpenAI 严格 JSON schema 支持不全，接第三方 LLM 前先测 `response_format` 兼容性。

### 3. 【关键】LLM 响应慢/不稳定是最大瓶颈，且受"高峰时段"影响
- DeepSeek 官方 API 单请求 40–150 秒（高峰期甚至 900 秒超时），随时段波动极大。
- 提高 `concurrent_requests` 只在本机并发上有效，**服务端排队是真正的瓶颈**——并发 3→6 无明显加速。
- 索引一次全量（第一卷）真实纯工作约 2.5–3 小时，但因踩坑重试实际耗时更长。
- **经验**：① 优先选响应快的模型（Kimi 单请求 2–6s，比 DeepSeek 快 20 倍）；② 错峰（DeepSeek 有峰谷定价）；③ 小语料先跑通，再上全量。

### 4. 【重要】Kimi 限流：组织级并发上限 3
- **现象**：GraphRAG 默认 `concurrent_requests: 25`，Kimi 账号并发上限 3 → 大量 429，重试后 workflow 失败。
- **解决**：`concurrent_requests: 1`（Kimi）或 6（DeepSeek 无此限）。
- **经验**：不同模型商的并发配额差异大，接新 provider 先压测。

### 5. 【重要】llama.cpp embedding 的 batch 上限
- **现象**：`input (2142 tokens) is too large to process. increase the physical batch size (current batch size: 512/2048)`。
- **根因**：llama-server 的 `--ubatch-size` 默认 512（后设 2048），长文本块（>2048 token）被拒。
- **解决**：`--batch-size 4096 --ubatch-size 4096`。
- **经验**：本地 llama-server 跑 embedding 前，batch 要覆盖最长 chunk；且**确认无残留旧进程占用端口**（否则新参数不生效）。

### 6. 【重要】向量维度必须匹配 embedding 模型
- **现象**：`Vector for document ... has dimension 1024, but index ... is configured with vector_size 3072`。
- **根因**：GraphRAG 默认 `vector_size: 3072`（OpenAI text-embedding-3-large 的维度），bge-m3 输出 1024。
- **解决**：在 `settings.yaml` 的 `vector_store.index_schema` 显式设 `vector_size: 1024`（三个字段都要）。
- **经验**：换 embedding 模型时，第一件事就是核对维度并更新 vector_store。

### 7. 【中等】Windows 中文编码问题（三处）
1. **GraphRAG 读取 .md 用系统默认编码**：文件是 UTF-8，但默认读成 GBK → 乱码。解决：`input.file_pattern` 匹配 .md 且确保 UTF-8（实际上文件读取正常，显示乱码是 PowerShell 问题）。
2. **CLI 输出中文在 PowerShell 显示乱码**：数据没坏，是终端编码。解决：Python 调用时设 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1`。
3. **settings.yaml 里正则 `$` 被当作模板占位符**：`file_pattern: .*\.md$` 报 `Invalid placeholder`。解决：去掉末尾 `$`（`.md` 足够）。
- **经验**：Windows + 中文 + YAML 正则，处处是坑；统一用 UTF-8 写文件、避免在 YAML 里放 `$`。

### 8. 【中等】MCP 注册会被 Codex 覆盖
- 手动改 `config.toml` 加入 `[mcp_servers.graphrag]` 会被 Codex 重写丢失。
- **解决**：用官方命令 `codex mcp add graphrag --env "GRAPHRAG_PROJECT=..." -- <cmd> <args>`，持久生效。
- **经验**：给 Codex 配 MCP 永远用 `codex mcp` 命令，不要手改配置文件。

### 9. 【中等】mcp 2.0 API 变化
- mcp 2.0 没有 `fastmcp` 子模块；`MCPServer.run(transport='stdio')` 是同步阻塞方法（无 `create_initialization_options`）。
- `call_tool` 返回 `CallToolResult` 对象（`res.content[0].text`），不是列表。
- **经验**：用 `server = MCPServer(name=...)` + `@server.tool()` + `server.run(transport="stdio")`。

### 10. 【低】opencode.ai/zen/go 代理
- 该代理列出 deepseek-v4-flash 等模型，但 2026-08-04/05 期间调用 deepseek 返回 403/超时（**通道未恢复**）；其它模型（kimi-k3、qwen3.7-max、glm-5.2、minimax）可用。
- kimi-k3 输出价约 $15/M（推理模型），跑大索引不划算；官方 DeepSeek 便宜 20 倍。
- **经验**：第三方代理模型清单 ≠ 可用性；跑大批量任务前先测真实可用性与价格。

## 七、补充发现（2026-08-05）：opencode 的 DeepSeek 其实可用 —— 关键在"走 CC Switch 本地代理"

### 现象
- 直接连 `https://opencode.ai/zen/go/v1/chat/completions`（带正确 key）→ 403 / 超时。
- 但 Claude Code（通过 CC Switch 代理）用同一端点正常，无超时。

### 根因
- CC Switch 本地代理（`http://127.0.0.1:15721`）维护到 opencode 的长连接（keep-alive/重试/连接池），
  直连时网络握手/路由可能卡住，代理转发则稳定。
- 实际生效的 key 是 CC Switch 当前 provider 的 `sk-****`（不是早前测试的 `sk-****`）。
- 代理对 Anthropic 格式（`/v1/messages`）和 OpenAI 格式（`/v1/chat/completions`）都转发，均可用。

### 实测（经 127.0.0.1:15721）
| 端点 | 结果 |
|---|---|
| `/v1/messages` (deepseek-v4-flash) | HTTP 200, ~10s |
| `/v1/chat/completions` (deepseek-v4-flash) | HTTP 200, ~12s |

### 经验
1. **第三方代理的"可用性"必须以实际走通的路径为准**——CC Switch 代理是可信的转发通道。
2. **测试 provider 时要复刻真实调用路径**（经代理 vs 直连差异巨大）。
3. 用代理跑 GraphRAG 时：`api_base: http://127.0.0.1:15721`，注意与 Claude Code 共用连接/配额，避免互相影响。
4. 若代理对 GraphRAG 的 `response_format`（json_object）兼容，可大幅提速（~10s vs 官方 106s）。

## 八、补充结论（2026-08-05 晚间）：opencode 通道完整探索与最终判定

### 背景
为加速合并版（119 块）索引，尝试利用 opencode.ai/zen/go 上的 DeepSeek（CC Switch 代理同源通道）。

### 探索过程与结论（全部实测）
1. **端点与密钥**：`https://opencode.ai/zen/go/v1/chat/completions` + CC Switch 当前 provider 的 key（`sk-****`）可连通；`/v1/models` 列出 deepseek-v4-flash 等。
2. **opt in 门槛**：早期调用返回 403 "requires explicit opt in"——DeepSeek 需在 opencode 网页显式启用中国托管版。用户 opt in 后 403 消失（变 500/超时 → 最终稳定 200）。
3. **response_format 参数不兼容**：opencode 对 `response_format`（含 json_object）返回 400 空 body。GraphRAG 社区报告补丁原用 `response_format_json_object=True`，已改为完全不传该参数、靠 prompt 约束 JSON 输出（实测可解析，3-4s）。
4. **速度真相**：短文本单请求 3-5s（看似很快）；但 GraphRAG 实体抽取的大文本块（1200 token + 输出大量实体/关系 JSON）实测 **3-4 分钟/块**——与官方 DeepSeek 相当，无速度优势。并发 1 与并发 4 均如此（瓶颈在 opencode 后端生成，非本机并发）。
5. **CC Switch 代理分流**：经代理（127.0.0.1:15721）时，GraphRAG 请求被识别为 Codex 类型并 failover 到官方 DeepSeek，未真正走 opencode。

### 最终判定
- **opencode 通道对 GraphRAG 无实际加速价值**（大文本块下与官方同速），且多一层 opt in + response_format 不兼容的复杂度。
- 合并版索引仍以 **官方 DeepSeek 为保底方案**（8-15h，~25-45 元）或 **Kimi 为快解**（2-4h，~35 元）。
- opencode 的价值仅限轻量短请求（如对话），不适合 GraphRAG 的批量长文本抽取。

### 可复用结论
1. 第三方代理"单请求快"≠"批量抽取快"——必须用**真实任务负载**测试，而非短文本 ping。
2. 接新 provider 先测：`response_format` 兼容性、大文本块耗时、并发行为。
3. opencode 的 DeepSeek 需 opt in（中国托管版），未 opt in 一律 403。

## 2026-08-05 下午 · 重大突破：opencode Go 通道打通（推翻早前判定）

> ⚠️ 早前"opencode 无实际加速价值"的结论**已过时**。根因是当时未发现 `reasoning_effort` 问题：opencode 的 deepseek-v4-flash **默认思考全开**，会把全部 max_tokens 烧在 reasoning_tokens 上、输出为空，所以实测 3-4 分钟/块是"纯思考"假象。关闭思考后单块 ~40s，24 并发全量索引仅 ~35 分钟，费用 0。

### 1. 本地网关真相：CC Switch 本地代理
- 真正能用的"本地网关"是 **CC Switch 的本地代理 `http://127.0.0.1:15721/v1`**（CC Switch 已登录 opencode Go，自动处理认证与路由）。
- `opencode serve`（headless）暴露的是 Web UI + 自有 REST API（/session 等），**不是 OpenAI 兼容端点**，GraphRAG 无法直连。
- 直连 `https://opencode.ai/zen/go/v1` 需 IPv4（Python 默认解析 IPv6 会握手卡死）+ 全套 `x-opencode-*` 头，且小请求偶发 500；经 CC Switch 代理稳定。

### 2. 关键配置（settings.yaml）
```yaml
completion_models:
  default_completion_model:
    model_provider: openai
    model: deepseek-v4-flash
    call_args:
      extra_body:
        reasoning_effort: none   # ← 关键！关闭思考，否则输出为空
      max_tokens: 12000
    api_base: http://127.0.0.1:15721/v1   # CC Switch 本地代理
    api_key: dummy
concurrent_requests: 24
```
- `call_args` 是 `ModelConfig` 的透传字段，会合并进每次 LiteLLM 调用。`reasoning_effort` 直接传会被 LiteLLM 丢弃，必须放 `extra_body` 里。

### 3. 速度与成本（真实负载）
- 大文本实体抽取：~40s/块（关闭思考后）；管线平均 **9.76s/请求**。
- 全量合并版（119 块，24 并发）：LLM 部分 ~15 min + 本地 bge-m3 向量化 ~20 min = **~35 min 完成**。
- **费用 = 0**：Go 订阅制（deepseek-v4-flash ~15.8 万次/月），本次 ~2318 请求 / 493 万 tokens，九牛一毛。

### 4. 社区报告 JSON 容错三层修复（947 失败 → 500/500）
模型输出 JSON 的常见瑕疵与对策（补丁在 `community_reports_extractor.py`）：
1. **代码围栏** ```json ... ``` → `_extract_json` 剥离围栏
2. **尾逗号 / 杂散文本** → 截取首 `{` 到末 `}` + 正则清尾逗号
3. **字符串内未转义 ASCII 引号**（如 `The "O|O"...`）→ `json_repair.loads` 兜底（已预装）
- 失败重试策略：失败响应已缓存在 LLM 层 → 补丁升级后重跑即缓存命中修复，无需重新调模型。
- 顽固社区（如 379，连官方 DeepSeek 也失败）→ 用 GraphRAG 自己的 `build_local_context`+`build_level_context` 复现生成，再补插 parquet + 手动补向量（lancedb 1024 维）。

### 5. 合并版最终数据（对比第一本）
| 指标 | 合并版 | 第一本《太素神境》 |
|---|---|---|
| 实体 | 3,709（2,394 有关联）| 1,623 |
| 关系 | 4,773 | 4,361 |
| 社区 / 报告 | 500 / 500 | 450 / ~ |
| 文本块 | 119 | — |
| tokens | ~493 万 | — |
- **观察**：35% 实体（1,315 个）无任何关系（孤立）。10 类 entity_types 下抽取偏"广"，可后续用 prompt 收紧（要求仅保留有明确关系的实体）。

### 6. 可复用清单
1. 接新 provider 必须关思考（reasoning_effort/thinking off），否则"慢"多半是空转。
2. LiteLLM 传参：能放 `extra_body` 就不要直接传顶层参数。
3. 大并发（24）走 CC Switch 代理没问题（0 重试）；opencode Go 有 5 小时/周/月配额，注意监控 429。
4. JSON 解析永远要三层容错（围栏→修复→json_repair）。

## 附：opencode 与 DeepSeek 官方关系调研（2026-08-05）

### 结论一句话
opencode 是**网关（gateway）**，其 Zen / Go 套餐里的 DeepSeek 系列**直接路由到 DeepSeek 官方 API**（使用 opencode 自己的聚合账号），模型本体就是官方同一模型；定价与官方一致（输入 $0.14/M ≈ ¥1/M、输出 $0.28/M ≈ ¥2/M）。但中间层会改写请求/响应，且共享上游账号，所以体感"不如官方直连"。

### 证据链
1. **官方文档**：opencode.ai/docs/zen 自述 Zen 是 "AI gateway"，模型经团队 "tested and verified" 后提供；Bifrost 文档称 Zen/Go 是 "gateway providers... that proxies to a curated set of models from multiple underlying providers"。
2. **定价一致**：Zen 的 deepseek-v4-flash 输入 $0.14/M、输出 $0.28/M，与 DeepSeek 官方平时价（¥1/¥2）完全一致（官方另有峰谷价 ¥2/¥4）。
3. **RegionError 证据**（本机 CC Switch 健康记录）：opencode-go 的 DeepSeek V4 Flash 曾报 403 `RegionError: The latest version of this model is only available hosted in China and requires explicit opt in` —— 最新 checkpoint 只在境内托管，须在 opencode 网页勾选"路由到中国"（用户已操作）。
4. **上游账号证据**（GitHub issue #27598）：opencode-go 返回 "Insufficient Balance" 时，用户 Go 配额还有 50%——报错来自 **opencode 后端自己的 DeepSeek 上游账号余额**，非用户配额。Kimi / MiniMax 也有同类上游余额问题（各自独立上游账号）。
5. **协议受限**（issue #39829）：opencode-go 只提供 /v1/chat/completions，**不支持 Responses API**（deepseek-v4-flash 走 /v1/responses → 400 "Upstream request failed"）；DeepSeek 官方 0731 checkpoint 已原生支持 Responses API，但 opencode 未切换。Codex 风格客户端因此走不了 opencode-go。
6. **reasoning_content bug**（issue #36354）：opencode 后端对 DeepSeek V4 的 reasoning_content 处理有 bug，带 tools 的请求偶发 500；去掉 tools 即 200。

### 免费 flash 的真相
- `deepseek-v4-flash-free` 只通过 Zen（providerID=opencode）提供，**限时免费**，官方注明数据可能用于改进模型（反馈收集版）。
- 有未公开配额（GitHub issue #28166：报 "free usage exceed"），并发/速度不如付费。
- 付费（Go）里的 deepseek-v4-flash 与免费版是**两个不同的接入**：Go 消耗订阅配额并路由官方。

### 为什么"opencode 的 DeepSeek 不如官方直连"
1. 中间层改写/破坏请求（tools 参数、reasoning_content、Responses API 缺失）。
2. 共享上游账号：官方 incident（如 8/4 拥堵）→ opencode 上游也被限流/余额告警。
3. 免费档是"反馈收集"变体，能力/速度有折扣。
4. 模型本体相同，但"入口质量"不同——所以要求稳定/便宜时，**官方直连（api.deepseek.com）更优**。

### 本机现状（CC Switch 实测）
- 当前 Codex 走 CC Switch 本地代理 127.0.0.1:15721 → `https://api.deepseek.com`（官方，wire_api=responses）→ 即本会话运行在**官方 DeepSeek** 上。
- opencode-go（say101004 等）走 `https://opencode.ai/zen/go/v1`，健康检查 OK 但需已勾选中国路由。

### 解经模式（decode=true）—— 修"念经式回答"
- 现象：神学密语语料下，GraphRAG 默认回答忠实复读原文（"爱成为土壤…"），像念经。
- 根因：语料本身象征编码 + 查询提示要求扎根原文 + 无"翻译层"指令（且查询 completion 用 reasoning_effort=none）。
- 解法：MCP 新增 `decode` 参数，包一层解经者指令：① 平白翻译寓意（不复读）② 区分字面/象征 ③ 给可操作结论。
- 实测（drift + decode，2026-08-05，约 2.9 分钟）："爱成为土壤"→安全依恋/抱持性环境；"种子结出土壤"→存在先于本质/自我实现的预言；"六姬一体"→荣格自性化/IFS；"我必自救"→萨特式自由+行动指南。回答从"念经"变"解经"。
- 用法：抽象神学题（信/觉悟/爱/法）→ drift 或 local + decode=true；事实性检索（人名/事件/关系）不需要。
