## 摘要

本文介绍一个面向文本叙事与时间序列分析的多引擎因果分析工具链。系统由五个互补组件构成：TRACE 文本因果发现引擎、TRACE Web 服务、TRACE-to-EDM 桥接服务、EDM-Takens 动力学分析库及其 Web 服务；另附基于 GraphRAG 的《神纪》知识图谱成品。系统的目标不是以单一算法替代因果推断，而是把概念抽取、结构诊断、轨迹构造、非线性动力学重建、反事实审计和知识检索组织成一条可观察、可审计、可复现的实验管线。

与以算法性能为中心的论文不同，本文采用“系统论文”视角，提出四类评估问题：功能链路是否完整、跨模块契约是否一致、运行环境是否可复现、发布物是否具备可审计的清洁边界。基于 6.7.2 版本，本文报告了 149 项自动化测试通过、16 项便携审计全部通过、15 条文本的真实端到端链路通过、15 篇微信公众号公开文章的试点链路，以及 GraphRAG 数据版本与向量索引一致性检查通过。源码发布包仅由 Git 跟踪文件生成，未包含运行目录、密钥或模型权重，并通过 SHA256 manifest 与 fail-closed 条目检查。

我们认为，该项目已经达到“可运行的研究工具与工程系统”水平：核心链路、数据契约、错误处理、发布流程和文档体系均已闭环。但其科学有效性仍未完成：缺少独立观测数据、盲测基准、消融实验、第三方复现和大规模外部有效性研究。因此，本文的定位是系统实现与可复现性评估，而不是对因果发现算法有效性的最终证明。

**关键词**：因果发现；经验动态建模；收敛交叉映射；HAVOK；DoWhy；GraphRAG；可复现性；系统评估

## 1. 引言

文本叙事中包含事件、主体、时间关系和隐含动力，而时间序列分析关注状态变量随时间的演化。二者之间存在明显的表示鸿沟：前者以语义概念和关系为主，后者要求数值化、等长、可嵌入的轨迹。现有工具通常在各自领域内成熟，但把“文本因果假设”转换为“动力学检验输入”，再把结果以可追溯方式返回给用户，仍缺少统一工程路径。

本项目尝试解决三个工程问题：

1. 如何从自然语言文本中形成可计算的概念关系；
2. 如何把概念关系转换为 EDM/CCM/HAVOK 可处理的轨迹矩阵；
3. 如何让不同算法、Web 服务、审计字段和发布物之间保持契约一致。

本文不主张 TRACE、CCM、HAVOK 或 DoWhy 本身是新的。本文的贡献在于系统组织与工程收口：

- 建立从文本到动力学的端到端管线，并显式标注合成 SEM 与观测数据的区别；
- 将大路由拆分到 route/service/repository 分层，删除 Web 端算法副本，形成单一算法源；
- 为 TRACE-to-EDM 定义稳定的轨迹 CSV 契约和错误传播机制；
- 为 GraphRAG 增加 provider 能力探测与运行时回退，避免依赖 `site-packages` 补丁；
- 建立文档链接检查、运行残留清理、干净源码包构建和 fail-closed 发布审计；
- 通过真实 E2E 而不仅是静态文件检查，验证多服务链路。

## 2. 系统定位与科学边界

### 2.1 系统是什么

该系统是一个“研究工具链”，而不是自动生成科学结论的黑箱。它帮助研究者完成：

- 从文本中提取候选概念和关系；
- 对候选结构执行统计诊断和反事实审计；
- 将概念轨迹送入非线性动力学分析；
- 将结果组织成可导出的图表、表格和 JSON；
- 通过 GraphRAG 在大型文本语料中检索实体、社区和上下文。

### 2.2 系统不是什么

系统不能仅凭 ATE、CCM rho 或 HAVOK 特征自动证明现实世界的因果关系。尤其需要注意：

- TRACE LIGHT/DEEP 默认可能在合成 SEM 数据上估计 ATE；
- `simulation=false` 不等同于“使用观测数据”；
- CCM 的相关映射技能不是实验干预；
- HAVOK 的强迫项定位是动力学诊断，不是因果识别；
- GraphRAG 的实体关系来自文本抽取，不是事实数据库。

因此，本文把 `data_source`、审计 verdict、样本量、嵌入参数和局限性作为系统输出的一部分，而不是附注。

## 3. 系统架构

### 3.1 三条使用路径

系统提供三条路径：

**路径 A：纯时间序列分析**

```text
CSV → edm-takens-web → EDM/CCM/HAVOK → 图表与 JSON 摘要
```

**路径 B：文本到动力学的完整链路**

```text
文本 → trace-engine-web → trace-engine → trace-to-edm
     → 轨迹 CSV → edm-takens-web → EDM 分析 → 回传结果
```

**路径 C：SUPER 模型路径**

```text
文本 → trace-engine-web → LLaMA Worker
     → token-level 因果发现 → 六战士诊断 → 结果展示
```

三条路径共享结果披露、任务状态和服务健康检查，但使用不同的计算后端。

### 3.2 主要组件

| 组件 | 角色 | 主要技术 |
|---|---|---|
| `trace-engine` | 文本因果发现与诊断 | Python、jieba、DoWhy、causal-learn、PyTorch |
| `trace-engine-web` | 文本分析 Web 服务 | Node.js、Express、SSE |
| `trace-to-edm` | 轨迹构造与桥接 | Node.js、Python、CSV 契约 |
| `edm-takens` | EDM/CCM/HAVOK 算法库 | Python、NumPy、SciPy、pyEDM |
| `edm-takens-web` | 时间序列分析服务 | FastAPI、Vite |
| `GraphRAG-神纪图谱` | 文献知识图谱与 MCP | GraphRAG、LanceDB、MCP |

### 3.3 单一源码源

6.7.0 版本删除了 `edm-takens-web/backend/edmtakens/` 算法副本。Web 后端直接导入 `edm-takens/src`，并通过 `sync_check.py` 阻止副本复活。这一改动减少了：

- 同一算法多份实现造成的修复遗漏；
- Web 与 CLI 行为不一致；
- 发布包体积和审计复杂度；
- “同步成功但实际是旧代码”的隐性错误。

## 4. 方法

### 4.1 TRACE：文本概念与因果结构

TRACE 的核心流程包括文本切分、概念抽取、关系构建、显著性过滤和诊断。系统提供 LIGHT、DEEP 和 SUPER 三种模式：

- LIGHT：快速概念图与简化诊断；
- DEEP：完整六战士诊断，包括 DoWhy、causal-learn、反事实桥接和审计；
- SUPER：使用 LLaMA 进行 token-level 因果发现。

六战士被明确分为“真算法层”和“启发式诊断层”。其中 CCM 与 EDM 在 Web 快速分析中的部分实现属于诊断近似，不应被表述为独立的真实因果证据。该分层是系统可信度设计的一部分。

### 4.2 TRACE-to-EDM：轨迹构造

桥接层将 TRACE 输出的概念矩阵转换为 EDM 可使用的 CSV。当前契约包含 89 列，除基础元数据和三层概念变量外，还包含：

```text
trace_status
trace_error
trace_mode
trace_data_source
```

其中 `trace_data_source=synthetic_sem` 明确表示 ATE/CI 来自合成 SEM 数据。桥接层还负责：

- 项目隔离；
- 数据集导入与导出；
- 任务状态与错误传播；
- 输出目录按需创建；
- 临时 ID 文件通过环境变量传给 Python，避免路径转义问题。

### 4.3 EDM-Takens：非线性动力学重建

EDM-Takens 提供 Takens 嵌入、Simplex 预测、S-Map、CCM、HAVOK、交叉验证和质量审计。

Takens 嵌入可写为：

```text
x(t) = [x_t, x_(t-τ), ..., x_(t-(E-1)τ)]
```

CCM 通过检验从一个变量重构的流形是否能预测另一个变量来判断方向性。其关键不是单次相关系数，而是随库长度增加时预测技能是否收敛。

HAVOK 将系统写成间歇强迫的线性动力系统：

```text
dV/dt = A V + B v
x = V r
```

其中 `V` 是 SVD 模态，`v` 是强迫项。系统同时报告 Hankel 比例、SVD 能量截断、近常量退化、Lyapunov 视界和审计 verdict。

### 4.4 GraphRAG：知识图谱与 MCP

GraphRAG 组件将大型文本语料构建为实体、关系、社区和文本块索引，并通过 MCP 暴露查询接口。当前归档包含：

- 3,038 个实体；
- 3,987 条关系；
- 555 个社区报告；
- 119 个文本块；
- 3 个 LanceDB 向量索引；
- 8 组实体别名。

系统通过 `data_version.json` 记录计数和文本块 hash，并通过 `verify-env.py` 检查 U+FFFD、索引 ID、向量同步和别名冲突。

### 4.5 结果披露原则

每类结果都应回答三个问题：

1. 数据来自哪里？
2. 算法是否真实执行，还是启发式回退？
3. 哪些结论不能从当前结果推出？

6.7.0 版本通过 `data_source`、`trace_status`、`trace_error`、`trace_mode`、审计 verdict 和 UI 警告来实现这一原则。

## 5. 可复现性与发布工程

### 5.1 Python 解释器

解释器探测不再写死本机盘符，候选顺序为：

```text
组件显式变量
→ Complement/.venv
→ COMPLEMENT_PYTHON_CANDIDATES
→ py -3.13 / -3.12 / -3.11 / -3.10
→ PATH 中的 python/python3
```

若缺少关键模块，启动阶段直接给出缺项与安装建议，而不是等到分析中段失败。

### 5.2 依赖与锁文件

- 三个 Node 项目保留 `package-lock.json`；
- 五个 Python 子项目保留 `requirements.txt` 与参考 lock；
- GraphRAG 保留独立 `requirements.txt`；
- 模型权重作为独立 artifact，不进入源码包。

### 5.3 运行残留清理

`clean_runtime.ps1` 默认 dry-run，区分两类清理：

- 安全清理：日志、缓存、临时文件、空脚手架；
- 显式历史清理：`-IncludeTaskHistory`，可删除任务输入、结果、归档与 SQLite。

脚本拒绝仓库外路径和 `.git` 目标。

### 5.4 发布包

`build_release.ps1` 的实现原则是“Git 跟踪文件定义发布物”：

1. 要求工作树干净；
2. 运行文档链接检查；
3. 运行便携审计；
4. 使用 `git archive HEAD` 生成 ZIP；
5. 拒绝 `node_modules`、运行目录、日志、密钥、SQLite、模型权重和本机配置；
6. 检查必需文件；
7. 生成 SHA256 manifest。

### 5.5 性能工程

6.7.2 在批处理路径上增加了六类优化：

- **TRACE 内容寻址缓存**：按 `sha256(version + mode + text)` 缓存 `result.json`，相同文章不重复分析；
- **常驻 Python Worker**：`py_bridge_worker.py` 在一个进程中复用 Python 与 Skill 模块导入；
- **有界 L1 预取**：TRACE L1 可并行预取，L2/L3 保持顺序执行以保护会话级历史；
- **EDM 结果缓存**：对轨迹内容、目标列、嵌入维度和时间窗做内容寻址缓存；
- **Qwen 语义嵌入缓存**：跨分析复用同一文本的 1536 维嵌入，可通过 `tools/warm_semantic_cache.py` 预热；
- **轻量 EDM 触发与设备回退**：Web 路由使用 `edm_only.py`；N<30 exploratory 时跳过不可靠的 CCM 批次。CUDA 显存不足时自动改用 CPU，避免 FP16 层溢出导致的数量级变慢。

缓存和 worker 都位于 Git 忽略的运行目录；`TRACE_CACHE_DISABLE=1`、`EDM_CACHE_DISABLE=1` 与 `TRACE_EMBEDDING_CACHE_DISABLE=1` 可禁用。
`TRACE_PREFETCH_WORKERS` 默认 2，建议根据内存与 CPU 调整到 2–4；不建议在未测内存的情况下直接开到 8。
`QWEN_DEVICE=cpu` 可显式选择 CPU 推理，`QWEN_LOAD_IN_4BIT=auto` 在可用显存足够时启用 4-bit。

| EDM 分析（N=15 fast small-sample） | 约 50–70 秒 |
| 优化后整链 | 约 1.5–2 分钟 |

该试点揭示了三个重要事实：

1. **工程链路可用**：真实微信公众号长文可以进入数据集、完成 TRACE 分析、生成 89 列轨迹并触发 EDM。
2. **LIGHT 模式存在明显同质化**：15 篇不同文章都得到 12 个概念和 12 条边，说明当前 LIGHT 概念图对文章差异的区分度有限。
3. **短样本动力学推断不可靠**：N=15 时，EDM 的 HAVOK 退化、CCM 0/6 显著、后审计为 WARN。这是样本量与数据形态的客观限制，不能据此宣称新闻事件之间存在稳定因果关系。

因此，这一试点支持“系统可用”的判断，同时不支持“科学结论已成立”的判断。

## 8. 讨论

### 8.1 工程优势

1. **端到端闭环**：文本、桥接、动力学分析、结果披露和发行包在同一仓库内。
2. **可追溯性**：`data_source`、审计 verdict 和错误字段使结果边界可被程序读取。
3. **去副本化**：算法单一真源减少了 Web/CLI 分叉风险。
4. **真实 E2E**：测试不仅检查文件存在，还启动服务并跑通链路。
5. **发布可审计**：源码包、manifest、条目白名单和文档检查构成可重复的发布流程。

### 8.2 科学局限

当前最关键的不足不是代码，而是科学证据：

- 缺少独立观测数据上的盲测；
- 缺少与成熟基准方法的系统比较；
- 缺少消融实验和样本量稳定性分析；
- 缺少第三方独立复现；
- 历史新闻实验缺少完整原始输出；
- 合成 SEM 结果不能替代观测因果估计；
- GraphRAG 的知识图谱质量仍需人工标注评估。

### 8.3 产品化局限

- 尚无统一 wheel/安装器；
- 完整离线运行包仍依赖外部模型权重和 llama-server；
- 无专用 CI E2E runner；
- 无截图视觉回归基线；
- 主要验证环境为 Windows，跨平台行为仍需系统测试。

### 8.4 完成度判断

| 维度 | 判断 |
|---|---|
| 核心功能链路 | 高：真实 E2E 通过 |
| 工程可维护性 | 较高：路由/服务拆分、单一源码源、测试覆盖 |
| 可复现性 | 较高：锁文件、解释器探测、发布审计 |
| 科学有效性 | 低至中：缺少独立观测验证与外部基准 |
| 产品化程度 | 中：源码可发布，完整离线包和安装器未闭环 |
| 文档完整度 | 高：架构、部署、调试、依赖、安全与维护文档齐全 |

因此，更准确的定位是：**已经可以作为研究工具和工程平台使用，但尚不能作为已验证的科学仪器对外主张因果结论。**

---

## 9. 结论

本文从系统论文角度评估了一个多引擎因果分析工具链的 6.7.2 实现。结果表明，该系统已经具备完整的文本到动力学分析链路、明确的数据来源披露、可复现的解释器与依赖策略、真实 E2E 验证和可审计的发布流程。

其下一阶段的关键任务不应继续堆叠功能，而应转向科学验证：建立独立观测数据集、预注册分析方案、增加基线比较和消融实验、完成第三方复现，并把模型权重、运行环境和实验原始输出纳入可长期引用的 artifact。

在这些工作完成之前，最诚实的结论是：

> 这是一个完成度较高的研究工具链与工程系统，但还不是一个已经完成科学验证的因果推断仪器。
