# 研究健全性：算法之外的把关

`havok.md`、`edm.md`、`validation.md` 处理的是"算法本身有没有做对"。这一节处理一个更高层的问题：**即便每一步算法验证都做对了，整个研究/开发过程本身，依然可能因为一些和算法无关的操作习惯，而滑向不可信**。这一节是给"vibe coding"场景的具体操作纪律——写代码时，把下面这些当成和写测试用例同等优先级的事项，而不是事后才补的论文礼仪。

## 1. 花园分叉路径问题（Garden of Forking Paths）

流程里有好几个需要扫描的参数（E、τ、r、q、θ、观测量本身的选择）。如果操作方式是"试各种组合，直到某一组显得有意思"，即便每一步单独看都用了正确的方法（Gavish-Donoho 阈值、留出集验证），**整个过程作为一个整体，依然构成研究者自由度过高的问题**——只要允许自己在足够多的分岔口做选择，几乎总能找到一条看起来"显著"的路径，即便真实信号根本不存在。这和 HARKing（Hypothesizing After Results are Known，看到结果后再声称"我早就这么猜"）是同一个问题的两种表现。

**vibe coding 时的具体做法**：把参数选择的决策规则写成代码里**固定的、自动化的函数**（比如"E 由留出集预测技能唯一确定"），而不是写成一个可以随手改的手工参数，然后凭结果好坏去调它。决策规则一旦被写死成自动化流程，花园分叉路径就被大幅收窄了；一旦决策规则本身也会因为"哪个结果好看"而被修改，无论算法多严谨，整个流程已经被污染。

## 2. 替代数据的数量：精确算出来，而不是拍脑袋

`validation.md` 提到"至少 20-100 份"，这里给出精确依据：N 份替代数据加 1 份真实数据，在原假设成立时这 N+1 个值是可交换的，真实数据恰好最极端的概率是 1/(N+1)。要单侧 p<0.05 的分辨率，至少需要 **19 份**；要 p<0.01，至少需要 **99 份**。如果这份分析可能会被写进正式材料，建议直接用 99 份或更高——审稿人几乎必问这个数字的依据，提前说清楚能省很多事。

## 3. 预注册：提前下注，而非事后欣赏

这是我们在算法层面反复强调的"拉卡托斯判准"（进步纲领需要提前给出可能失败的预测），在研究操作上的具体落地：**在跑正式分析之前，先写一份带时间戳的文档（哪怕只是一次 commit），写清楚这次分析预期会看到什么、用什么标准判定成立或不成立**，然后再运行分析。这份文档的存在，是区分"提前下了一个可能会输的赌注"和"看到结果后把它包装成早有预料"的唯一可靠证据，也直接解决了第1条的花园分叉路径问题——规则提前写死，就没有空间事后悄悄改选。

**vibe coding 时的具体做法**：每次正式分析前，先让 AI 助手生成一份 `preregistration.md`（或直接写成一段带时间戳的 commit message），列出本次分析的参数决策规则、显著性阈值、预期结果的方向，再执行分析脚本。

## 4. 完整记录超参数与环境

每一次分析都要完整记录：E、τ、r、q、θ、替代数据生成方法与份数、随机种子、训练/测试集的精确切分时间点、软件包版本。没有这些记录，**任何人（包括未来的你自己）都无法重复这次分析**——而"可被重复"是区分科学主张与自说自话的最基本门槛。

**vibe coding 时的具体做法**：把这些参数写进一个独立的 config 文件（json/yaml），每次运行分析时自动连同结果一起存档，不要散落在代码注释或脑子里。

## 5. 敏感性分析：不要只报告"最优参数"下的那一个结果

留出集交叉验证给出的"最优" E 或 θ，本身是从有限、含噪数据里估计出来的，自己也带不确定性。健全做法是**报告结果在"最优值 ±1"这类邻近参数下是否依然成立**。如果结论在 E=5 时成立、E=6 时完全消失，可信度要打问号——真实信号通常不会对参数的微小扰动如此脆弱。

**vibe coding 时的具体做法**：不要只跑一次最优参数下的分析，写一个循环，把最优值附近的一小圈参数都跑一遍，把结果的稳定性作为报告的一部分。

## 6. 正负对照组：用已知答案的合成数据先标定流程——但绝不能反过来填补真实数据

替代数据检验回答"结果是否显著优于噪声"，但还有一层更进一步的校准：**先用一个真实因果结构/非线性程度完全已知的合成数据集**（经典洛伦兹系统，或自己编写的、已知因果方向的耦合系统）跑一遍完整流程，确认流程能正确恢复出已知答案，且在与真实数据相近的噪声水平和序列长度下依然有效。这一步给出的是**在这个具体数据体量和噪声水平下，流程本身的假阳性率/假阴性率大概是多少**，而不是仅依赖渐近理论"大样本下应该没问题"的空头保证。

### ⚠️ 硬性红线：标定数据 ≠ 数据增强，两者绝不能混淆

这一条必须单独强调，因为极容易被误读成"数据不够就自己生成一些"——这是完全错误的方向，会直接违背非线性/混沌方法的存在理由，必须严格区分两件事：

**正当做法（标定，calibration）**：合成数据集**从头到尾保持与真实数据完全隔离**，只用来检验代码/流程本身有没有 bug（SVD 算得对不对、嵌入维度选择函数有没有 off-by-one、CCM 因果方向判断是否被正确实现）。合成数据的结果**永远不进入真实数据的分析管线**，它只回答"我的代码可信吗"，不回答"我的真实系统是什么样的"。

**绝对禁止的做法（数据增强，augmentation）**：用插值、bootstrap 重采样、或用小样本训练出的生成模型，去"造出更多点"直接填补或延伸真实的、量太小的数据本身。这在混沌系统场景下是自我矛盾的，原因分三层：
- **插值**隐含地假设轨迹在采样点间光滑变化，但混沌系统对初始条件的极端敏感依赖，意味着真实轨迹在两个观测点之间可能已经历远比"光滑插值"更剧烈的展开——插值出来的中间点，描绘的是一条被光滑性假设强行拉直的、并不存在的轨迹。
- **Bootstrap 重采样**的合法性建立在样本可交换的前提上，混沌序列恰恰相反，其定义性特征就是序列内部存在紧密的、非线性的序列依赖（这正是延迟嵌入想捕捉的东西）——对混沌数据做 bootstrap，等于直接破坏了你想研究的那个对象本身。
- **用小样本训练生成模型去"造数据"**是最危险的一种：生成器几乎必然只是在记忆/放大原始几十个点里的噪声结构，"生成"出的数据只是把噪声伪影重新排列。后续拿这批数据跑 HAVOK/EDM，几乎注定会"发现"某种非线性结构——因为这个结构是生成器自己织进去的，不是真实系统的。这是数据处理不等式在时间轴上的翻版：真实观测点里蕴含的关于系统真实吸引子的信息量是一个上限，任何后续生成操作都不可能凭空往这个上限里注入新信息。

**判断数据量是否足够的具体标尺**：混沌系统有一个特征时间尺度——李雅普诺夫时间（1/最大李雅普诺夫指数），两条原本无限接近的轨迹因指数级发散而彻底"失联"所需的时间。延迟嵌入要真正覆盖吸引子的整体几何形状，通常需要观测序列长度达到这个李雅普诺夫时间的许多倍。如果真实数据的时间跨度还不到几个李雅普诺夫时间，关于吸引子全局几何形状的信息，原本就没有被系统"演化"出来给你观测到——这是信息从源头就不存在的问题，不是可以靠后期数据处理弥补的工程问题。

**真正的出路**：如果诚实评估后发现数据量确实不足以支撑可靠的吸引子重建，**正确做法不是想办法生成更多点去凑数，而是回到主 `SKILL.md` 第一步的路由逻辑，换用贝叶斯状态空间模型**——这类方法的设计初衷，就是在承认"数据不够、无法可靠重建吸引子"这个事实的前提下，依然给出一个诚实的、带着恰当不确定性的推断，而不是伪造出重建吸引子所需的数据量。

**标定本身也有局限，需要诚实报告为区间而非单点**：用洛伦兹系统跑出来的假阳性率/假阴性率，只精确对应洛伦兹系统自己的维度、李雅普诺夫指数、噪声敏感度，并不保证真实系统（这些属性未知）会有相同的错误率——如果已经完全知道真实系统的这些属性，一开始就不需要用 equation-free 方法了。缓解方法：构造一组跨越不同维度、不同李雅普诺夫指数、不同噪声水平的合成系统家族，覆盖领域知识认为真实系统可能落在的合理范围，报告"在这个参数范围内，流程的假阳性率大致在什么区间"，而不是假装标定出了一个精确数字——这与情景规划优于单点预测是同一个精神：无法消除关于真实系统的不确定性，但可以诚实地把这份不确定性体现在报告的置信区间里。

**vibe coding 时的具体做法**：在正式分析真实数据之前，先让 AI 助手写一个合成数据生成器（已知答案，且最好是一组覆盖不同参数的家族而非单一洛伦兹系统），完整跑一遍流程作为"单元测试"，确认流程本身没有系统性偏差，再应用到真实数据上——但生成器产出的任何数据点，都不得以任何形式拼接、插值或掺入真实数据集，两条数据管线必须在代码层面物理隔离（建议放在不同目录/不同变量命名空间，避免误用）。

## 7. 探索性 vs 验证性：在任何书面材料里明确标注

如果一项分析是看到数据后才决定要测试的假设，必须标注为"探索性"，不能用验证性研究的语言（"我们发现X显著导致Y"）来叙述。这不是文字游戏，是给未来的读者（包括你自己）一个诚实信号：这个结论目前是"值得用新数据验证"的阶段，还是已经真的通过了一次独立的、预先设计好的检验。

**vibe coding 时的具体做法**：让输出报告的代码模板里，自动带上一个"本次分析性质：探索性/验证性"的标注字段，强制自己每次都做这个判断，而不是事后才想起来。

## 与主技能其余部分的关系

这一节和 `validation.md` 不是重复关系：`validation.md` 处理的是"这个具体的非线性度量是否真实存在"（替代数据检验、CCM 收敛性），是**单次分析内部**的算法把关；这一节处理的是"整个研究/开发流程作为一个整体是否可信"，是**跨越多次分析、多个参数选择、多个假设**的流程把关。两者都不能省，但省略的后果不同——前者省略会让你相信一个不存在的信号，后者省略会让你在多次尝试后凑出一个看起来存在、其实是选择性报告产物的信号。
